## 1. 引言

### 1.1 文档目的

本文档为合江汉代画像石棺数字化保护与展示利用项目的测试计划文档，定义项目的测试策略、测试方法、测试用例、测试环境和测试进度计划。本文档是测试团队开展测试工作的指导性文件，也是项目相关方了解测试范围和进度的参考依据。

### 1.2 测试目标

本项目测试工作围绕以下目标开展。

功能正确性目标要求所有功能模块按照需求规格说明书实现，功能逻辑正确，数据处理准确，接口调用符合规范。测试需覆盖所有功能点，确保无遗漏。

性能达标目标要求系统在指定负载下保持良好响应速度。具体指标包括首页加载时间不超过3秒，API接口响应时间不超过200毫秒，100个并发用户下系统正常运行。

安全性保障目标要求系统具备完善的安全防护机制，防止常见安全威胁。测试需验证认证授权、输入校验、数据加密等安全措施的有效性。

兼容性满足目标要求系统在不同环境和设备上正常运行。测试需覆盖主流浏览器、操作系统和移动设备。

### 1.3 测试范围

本项目测试范围覆盖以下内容。

前端测试范围包括游客端和管理后台的所有页面组件、三维渲染功能、全景漫游功能、表单交互功能、权限控制功能、响应式布局等。

后端测试范围包括所有RESTful API接口、业务逻辑处理、数据存取操作、缓存机制、文件上传下载、日志记录等。

集成测试范围包括前后端联调测试、三方服务集成测试（OSS、Redis、LLM API）、容器化部署测试等。

非功能测试范围包括性能测试、安全测试、兼容性测试、压力测试等。

### 1.4 测试排除项

以下内容不在本项目测试范围内。文物数据的学术研究和内容正确性验证由业务专家负责。第三方支付、短信等计费类服务不属于本系统功能。原生移动端应用（iOS、Android）不包含在本项目范围内。服务器硬件故障、网络中断等基础设施问题。

## 2. 测试概述

### 2.1 测试类型划分

本项目测试按测试阶段和测试对象划分为以下类型。

按测试阶段划分，测试分为单元测试、集成测试、系统测试、验收测试四个阶段。单元测试在开发阶段由开发人员执行，验证单个模块的功能正确性。集成测试在各模块开发完成后执行，验证模块间接口调用正确性。系统测试在所有模块集成完成后执行，验证系统整体功能完整性。验收测试由用户或用户代表执行，确认系统满足业务需求。

按测试对象划分，测试分为功能测试、性能测试、安全测试、兼容性测试四类。功能测试验证功能实现是否符合需求。性能测试验证系统响应速度和负载能力。安全测试验证系统安全防护措施有效性。兼容性测试验证系统在不同环境下的运行情况。

### 2.2 测试启动条件

各阶段测试的启动条件如下。

单元测试启动条件为开发人员完成单个模块编码并通过本地编译，代码已提交到代码仓库。

集成测试启动条件为相关模块的单元测试全部通过，接口契约文档已确认，测试环境已准备就绪。

系统测试启动条件为所有功能模块开发完成并通过集成测试，测试环境部署完毕，测试数据准备完成。

验收测试启动条件为系统测试全部通过，缺陷修复确认完成，测试报告已评审通过。

### 2.3 测试通过标准

测试通过需满足以下标准。

功能测试通过标准为所有测试用例执行通过，测试用例覆盖率达到100%，无严重及以上级别缺陷遗留。

性能测试通过标准为所有性能指标达到要求值，响应时间满足SLA约定，并发测试无崩溃无超时。

安全测试通过标准为无高危及以上安全漏洞，低危漏洞数量不超过5个，无中危漏洞遗留。

兼容性测试通过标准为所有目标浏览器和设备测试通过，页面布局正常，功能运行正常。

## 3. 测试策略

### 3.1 单元测试策略

单元测试由开发人员编写和执行，采用白盒测试方法，针对代码内部逻辑进行验证。

后端单元测试使用 Jest + ts-jest，测试文件与源码同目录（`src/**/*.spec.ts`）。当前已覆盖游客端埋点服务（浏览量累加、日志落库、在线访客更新、非法目标 ID 容错）。

前端单元测试规划使用 Vitest + Vue Test Utils，目前尚未建立组件单测，前端以 `npm run build` 类型检查/构建验证和浏览器实测为主。

单元测试代码需遵循项目编码规范，与业务代码存放在同一仓库中。测试代码需包含清晰的命名和注释，说明测试意图和预期结果。

### 3.2 集成测试策略

集成测试验证模块间接口调用和数据交互的正确性，采用自底向上的测试策略。

后端集成测试使用 Jest + Supertest（`npm run test:e2e`，配置 `test/jest-e2e.json`）。`test/visitor.e2e-spec.ts` 覆盖游客端公开接口：崖墓列表/详情、石棺列表/详情、全景在线过滤与草稿 404、公告 published 过滤；用例仅读取现有数据，不写入数据库。

前端集成测试目前未配置 Playwright/Cypress 脚本，采用浏览器手工走查游客端与后台核心路径，并在 `out/report/闭环验证矩阵.md` 记录结果。

第三方服务集成测试使用Mock Server模拟外部服务响应，验证系统与外部服务的交互逻辑。实际环境测试时使用真实服务验证集成正确性。

### 3.2.1 当前实际自动化覆盖与缺口

已落地：

| 范围 | 文件 | 覆盖内容 | 运行方式 |
|---|---|---|---|
| 游客埋点单元测试 | `hanheritage-api/src/modules/visitor/visitor.service.spec.ts` | 崖墓/石棺/全景事件日志、浏览量自增、在线访客、非法 ID 容错 | `npm test` |
| 游客公开接口 E2E | `hanheritage-api/test/visitor.e2e-spec.ts` | 无 JWT 读取崖墓/石棺/全景/公告；状态过滤与 404 | `npm run test:e2e` |

尚未自动化：后台登录与权限、崖墓/石棺/全景后台写操作、模型地址校验、上传文件清理脚本、游客端组件渲染。上述内容目前以接口实测与浏览器走查为准，后续可补 Playwright 用例。

### 3.3 系统测试策略

系统测试验证系统整体功能完整性和业务流程正确性，采用黑盒测试方法。

功能测试使用手动测试和自动化测试相结合的方式。核心功能使用自动化测试脚本保证回归效率，非核心功能使用手动测试验证细节交互。

数据测试验证数据的完整性、一致性和正确性。包括数据新增、修改、删除的正确性，数据关联的有效性，数据导入导出的准确性。

界面测试验证页面布局、样式、交互的符合性。使用截图对比工具进行页面回归测试，确保UI变更被及时发现。

### 3.4 性能测试策略

性能测试评估系统在不同负载下的响应速度和稳定性。

性能测试工具使用JMeter进行API接口性能测试，使用Lighthouse进行前端页面性能测试，使用nGrinder或Locust进行并发压力测试。

基准测试测量系统在正常负载下的响应时间，建立性能基准。负载测试逐步增加并发用户数，测试系统负载能力和性能拐点。压力测试在极限负载下测试系统稳定性和故障恢复能力。

性能测试环境需与生产环境配置一致或等比缩放，确保测试结果的可参考性。

### 3.5 安全测试策略

安全测试评估系统安全防护能力，发现并修复安全漏洞。

安全测试方法包括静态代码安全扫描、使用SonarQube进行代码安全扫描，检测SQL注入、XSS等常见漏洞。动态安全测试使用Burp Suite或OWASP ZAP进行渗透测试，模拟攻击验证防护措施。安全配置审计检查系统安全配置是否符合最佳实践，包括密码策略、会话管理、权限配置等。

安全测试覆盖认证授权、数据加密、输入校验、输出编码、会话管理等安全要点。发现的安全漏洞按风险等级划分，高危漏洞必须在上线前修复。

### 3.6 兼容性测试策略

兼容性测试验证系统在不同环境下的运行情况。

浏览器兼容性测试覆盖Chrome、Edge、Safari、Firefox等主流浏览器，每种浏览器测试最新版本和前两个大版本。使用BrowserStack或Sauce Labs进行多浏览器自动化测试。

操作系统兼容性测试覆盖Windows、macOS、Linux等桌面操作系统，测试各系统下浏览器的兼容性。

移动端兼容性测试覆盖iOS和Android系统的主流设备，测试移动浏览器的兼容性。重点测试响应式布局在小屏幕设备上的显示效果。

## 5. 测试环境

### 5.1 测试环境架构

测试环境采用与生产环境一致的架构，确保测试结果的可参考性。测试环境包括前端服务器、后端应用服务器、数据库服务器、缓存服务器。

测试环境网络与开发环境隔离，模拟真实生产网络环境。测试环境使用独立域名和SSL证书，模拟生产环境配置。

### 5.2 测试环境配置

测试环境服务器配置如下。

前端服务器使用2核4G云服务器，安装Nginx作为Web服务器。配置与生产环境一致的Nginx配置，包括反向代理规则和SSL配置。

后端服务器使用4核8G云服务器，安装 Node.js 20+ 运行环境（本项目后端为 NestJS）。配置与生产环境一致的应用参数，包括数据库连接池大小等。

数据库服务器使用4核16G云服务器，安装MySQL 8.0。配置主从复制架构，读写分离配置正确。

缓存服务器使用2核4G云服务器，安装Redis 7。配置持久化和哨兵或集群模式。

### 5.3 测试数据准备

测试数据包括基础数据和业务数据两类。

基础数据包括系统内置的字典数据、部门数据、角色数据、菜单数据等。基础数据在环境初始化时自动导入。

业务数据包括崖墓数据、石棺数据、全景数据、资源数据等。业务数据使用脱敏后的真实数据或模拟数据，数据量需满足性能测试需求。

测试数据存放在独立的测试数据库中，与开发数据隔离。测试数据可在测试前初始化，测试后清理，保证测试的独立性和可重复性。

### 5.4 测试工具清单

测试工作使用的工具如下。

前端测试工具：Vite 构建（`npm run build`）用于类型与产物校验；Vitest/Playwright 尚未接入。

后端测试工具包括 Jest（单元测试）、ts-jest、Supertest（HTTP 集成测试）、NestJS Testing 模块。实际命令：`npm test`、`npm run test:e2e`。

接口测试工具包括Postman（接口调试）、JMeter（性能测试和负载测试）。

安全测试工具包括SonarQube（代码安全扫描）、Burp Suite（渗透测试）、OWASP ZAP（动态安全测试）。

缺陷管理工具包括Jira或Redmine，用于缺陷提交、跟踪和管理。

## 6. 测试进度计划

### 6.1 测试阶段划分

测试工作分为准备阶段、执行阶段、回归阶段三个阶段。

准备阶段工作包括测试环境搭建、测试数据准备、测试工具部署、测试用例编写和评审。准备阶段预计耗时1周。

执行阶段工作包括单元测试执行、集成测试执行、系统测试执行、性能测试执行、安全测试执行。执行阶段预计耗时2周，与开发工作并行开展。

回归阶段工作包括缺陷修复验证、回归测试执行、验收测试支持、测试报告编写。回归阶段预计耗时1周。

### 6.2 测试里程碑

测试里程碑安排如下。

M1测试环境就绪里程碑在项目第2周末达成。测试环境搭建完成，测试数据准备完成，测试工具部署完成。

M2 单元测试完成里程碑在项目第4周末达成。后端单元测试覆盖率达标，前端单元测试覆盖率达标。

M3 集成测试通过里程碑在项目第6周末达成。所有模块集成测试通过，缺陷修复完成。

M4 系统测试通过里程碑在项目第8周末达成。功能测试全部通过，性能测试通过，安全测试通过。

M5 验收测试通过里程碑在项目第10周末达成。验收测试通过，系统可以上线。

测试执行期间，测试团队每日编写测试报告，包括以下内容。昨日完成测试用例数量和执行结果。新发现缺陷数量和严重程度分布。缺陷修复情况统计。阻塞测试执行的问题和解决方案。今日测试计划和风险提示。

测试团队每周编写测试周报，包括以下内容。本周测试进展总体评估。测试用例执行进度和覆盖率。缺陷统计和分析，包括新增、修复、遗留数量。本周发现的重要缺陷和解决方案。下周测试计划和风险预警。

## 7. 缺陷管理

### 7.1 缺陷严重等级

缺陷按严重程度分为四级。

致命缺陷（P0）指系统崩溃、数据丢失、核心功能完全不可用等严重影响业务运作的缺陷。发现致命缺陷需立即报告，24小时内提供修复方案。

严重缺陷（P1）指重要功能无法正常使用、数据计算错误、安全漏洞等影响系统正常使用的问题。发现严重缺陷需当天报告，3天内提供修复方案。

一般缺陷（P2）指界面显示问题、交互体验问题、非核心功能异常等问题。发现一般缺陷需及时记录，1周内提供修复方案。

轻微缺陷（P3）指样式偏差、文字错误、提示信息不准确等不影响功能使用的问题。轻微缺陷可批量修复，在下一版本中统一解决。

### 7.2 缺陷状态流转

缺陷状态流转如下。

新建状态（New）指缺陷被提交后的初始状态，由测试人员设置。确认状态（Confirmed）指开发人员确认缺陷有效并可重现。进行中状态（In Progress）指开发人员开始修复缺陷。已修复状态（Fixed）指开发人员完成缺陷修复，待测试验证。待验证状态（Pending Retest）指缺陷修复待测试人员验证。已关闭状态（Closed）指缺陷修复通过验证，测试人员关闭缺陷。重新打开状态（Reopened）指验证发现修复不完整，重新打开缺陷。

### 7.3 缺陷处理时效

缺陷处理需满足以下时效要求。P0缺陷需在4小时内响应，24小时内提供修复方案，48小时内完成修复。P1缺陷需在8小时内响应，3天内完成修复。P2缺陷需在1周内完成修复。P3缺陷可批量处理，在下一版本中统一修复。

### 7.4 缺陷关闭标准

缺陷关闭需满足以下标准。缺陷对应的测试用例执行通过。缺陷在多个测试环境验证通过。缺陷修复不影响其他功能。相关文档已更新（如有必要）。
