## 3. 实体关系分析

### 3.1 一对多关系

| 主实体 | 从实体 | 关系说明 | 外键列 |
|--------|--------|---------|--------|
| biz_cliff | biz_opening | 一个崖墓群包含多个墓口 | `cliff_id` |
| biz_coffin | biz_coffin_image | 一个石棺拥有多张成果图 | `coffin_id` |
| biz_coffin | biz_coffin_model | 一个石棺关联一个三维模型 | `coffin_id`(UNIQUE) |
| res_folder | res_file | 一个目录包含多个文件 | `folder_id` |
| res_folder | res_folder | 自引用：一个目录包含多个子目录 | `parent_id` |
| sys_dept | sys_user | 一个部门包含多个用户 | `dept_id` |
| sys_dept | sys_dept | 自引用：一个部门包含多个子部门 | `parent_id` |
| sys_menu | sys_menu | 自引用：一个菜单包含多个子菜单 | `parent_id` |
| sys_role | sys_role | 自引用：一个角色包含多个子角色 | `parent_id` |
| sys_post | sys_post | 自引用：一个岗位包含多个子岗位 | `parent_id` |

### 3.2 多对多关系

| 实体A | 实体B | 中间表 | 关系说明 |
|--------|--------|--------|---------|
| sys_user | sys_role | sys_user_role | 一个用户可拥有多个角色，一个角色可分配给多个用户 |
| sys_user | sys_post | sys_user_post | 一个用户可担任多个岗位，一个岗位可由多个用户担任 |
| sys_role | sys_permission | sys_role_permission | 一个角色拥有多个权限，一个权限可属于多个角色 |
| sys_post | sys_permission | sys_post_permission | 一个岗位拥有多个权限，一个权限可属于多个岗位 |

### 3.3 自引用关系详解

1. **部门树（sys_dept）**：通过 `parent_id` 实现无限层级部门树，原型中为3级结构（项目组→博物馆→信息中心/展教部）
2. **菜单树（sys_menu）**：通过 `parent_id` 实现两级菜单树（分组→叶子菜单），原型中7个分组、17个叶子
3. **角色树（sys_role）**：通过 `parent_id` 实现角色继承，原型中"系统管理员"→"业务管理员"→"内容编辑"
4. **岗位树（sys_post）**：通过 `parent_id` 实现岗位层级，原型中"馆长"→"副馆长"→"展教专员"
5. **资源目录树（res_folder）**：通过 `parent_id` 实现3级目录，原型中限制 `level` 为1-3

### 3.4 弱引用关系

以下关系在原型中通过名称字符串关联，正式环境应改为外键：

| 原型关联方式 | 建议改进 |
|-------------|---------|
| 石棺的 `tomb_group` 字段存储崖墓群名称字符串 | 改为 `cliff_id` BIGINT FK → biz_cliff.id |
| 崖墓群的 `panorama_file_name` / `model_file_name` 存储文件名 | 改为关联 res_file 或独立媒体资源表 |
| 操作日志的 `user_display` 存储显示名 | 保留冗余字段，同时增加 `user_id` FK |
| 全景资源的 `url` 直接存储外部链接 | 改为 `storage_path` 指向对象存储 |

## 5. 数据校验规则

### 5.1 崖墓群校验规则

| 字段 | 规则 | 原型来源 |
|------|------|---------|
| name | 必填，长度1-100 | cliff-page.js: `if (!name \|\| !town) return "请填写崖墓群名称并选择乡镇"` |
| town | 必填，须为合江县22个乡镇之一 | cliff-page.js: ADD_TOWN_OPTIONS |
| code | 格式 `CM-NN`，唯一 | cliff-page.js: `nextCliffCode()` + 唯一性检查 |
| lng | 精度5位小数，范围105.48~106.28 | cliff-page.js: MAP_BOUNDS |
| lat | 精度5位小数，范围28.48~28.98 | cliff-page.js: MAP_BOUNDS |
| level | 枚举值，5选1 | cliff-page.js: LEVEL_OPTIONS |
| category | 枚举值，4选1 | cliff-page.js: CATEGORY_OPTIONS |
| status | enabled/disabled | |
| address | 手动模式下，地址或经纬度至少填一项 | cliff-page.js: `if (!address && (!lng \|\| !lat))` |

### 5.2 墓口校验规则

| 字段 | 规则 | 原型来源 |
|------|------|---------|
| name | 必填 | cliff-page.js: `if (!name) return "请填写墓口名称"` |
| coord | 格式 `x:N.NN y:N.NN z:N.NN` | cliff-page.js: parseXYZCoord |
| 每崖墓墓口数 | 上限6个 | cliff-page.js: `if (openings.length >= 6)` |

### 5.3 石棺校验规则

| 字段 | 规则 | 原型来源 |
|------|------|---------|
| code | 格式 `SC-NN`，唯一 | coffin-page.js: 自动编号 |
| title | 必填 | |
| quantity | 正整数 | |
| dimLength/dimWidth/dimHeight | 非负数值 | |
| weightValue | 非负数值 | |
| weightUnit | 枚举：kg/g | |
| 三维模型文件 | 扩展名 .glb/.gltf | coffin-page.js: `accept=".glb,.gltf,model/*"` |
| 成果图文件 | 扩展名 .jpg/.jpeg/.png/.webp | coffin-page.js: `accept="image/jpeg,image/jpg,.jpg,.jpeg,image/png,.png,image/webp,.webp"` |
| 成果图数量 | 每类约4~5张 | coffin-page.js: 提示"单类约 4～5 张" |

#### 阶段三：localStorage数据迁移

对于已使用原型并产生localStorage数据的用户，提供迁移脚本：

```javascript
// 前端迁移脚本：读取localStorage并提交到后端API
function migrateLocalStorageToServer() {
  var KEY = "prototypeAdminSysConfigV1";
  var raw = localStorage.getItem(KEY);
  if (!raw) return;
  var data = JSON.parse(raw);

  // 1. 迁移菜单树
  if (data.menuTree) {
    fetch('/api/v1/menus/migrate', {
      method: 'POST',
      headers: {'Content-Type': 'application/json', 'Authorization': 'Bearer ' + token},
      body: JSON.stringify(data.menuTree)
    });
  }

  // 2. 迁移公告
  if (data.notices) {
    data.notices.forEach(function(n) {
      fetch('/api/v1/notices', {
        method: 'POST',
        headers: {'Content-Type': 'application/json', 'Authorization': 'Bearer ' + token},
        body: JSON.stringify(n)
      });
    });
  }

  // 3. 迁移个人资料
  if (data.profile) {
    fetch('/api/v1/profile', {
      method: 'PUT',
      headers: {'Content-Type': 'application/json', 'Authorization': 'Bearer ' + token},
      body: JSON.stringify(data.profile)
    });
  }

  // 迁移完成后清除localStorage
  localStorage.removeItem(KEY);
}
```

## 7. 接口版本管理与兼容性策略

### 7.1 版本策略

**URL路径版本控制：**

```
/api/v1/...    # 当前版本
/api/v2/...    # 未来版本（不兼容变更时）
```

**版本升级原则：**

| 变更类型 | 版本策略 | 示例 |
|---------|---------|------|
| 新增接口 | 小版本，不升级 | 新增 GET /api/v1/dashboard/spark |
| 新增可选请求参数 | 小版本，不升级 | 列表接口新增筛选字段 |
| 新增响应字段 | 小版本，不升级 | 响应增加统计字段 |
| 删除/重命名字段 | 大版本，升级v2 | 字段名变更 |
| 修改字段类型 | 大版本，升级v2 | integer→string |
| 删除接口 | 大版本，升级v2 | 废弃某接口 |

### 7.2 兼容性保证

1. **响应字段只增不减**：新增字段不影响现有客户端
2. **废弃字段标记**：使用 `@Deprecated` 注解，至少保留2个版本周期
3. **默认值兼容**：新增必填字段提供合理默认值
4. **分页参数标准化**：统一使用 `page`/`size`，默认值分别为1和20

### 7.3 API文档规范

- 使用 OpenAPI 3.0 规范生成接口文档
- 每个接口标注：版本号、变更记录、废弃标记
- 提供 Swagger UI 在线调试界面

## 8. 数据安全与隐私保护设计

### 8.1 认证与授权

| 安全措施 | 实现方案 |
|---------|---------|
| 认证方式 | JWT（Access Token + Refresh Token） |
| Token存储 | Access Token: 内存/HttpOnly Cookie; Refresh Token: HttpOnly Cookie |
| Token有效期 | Access Token: 2小时; Refresh Token: 7天 |
| 密码存储 | bcrypt（cost factor ≥ 12）或 argon2id |
| 密码策略 | 最少6位（原型规则），正式环境建议8位+大小写+数字+特殊字符 |
| 登录失败锁定 | 5次失败后锁定15分钟 |
| 会话管理 | Redis存储会话，支持单设备/多设备登录策略 |

### 8.2 权限控制

**RBAC权限模型：**

```
用户 → 角色 → 权限项
用户 → 岗位 → 权限项
```

**数据范围控制（dataScope）：**

| dataScope值 | 说明 | 数据过滤规则 |
|-------------|------|-------------|
| all | 全部数据 | 无过滤 |
| dept | 本部门数据 | WHERE dept_id = 当前用户部门ID |
| custom | 自定义数据 | WHERE dept_id IN (自定义部门ID列表) |

**接口级权限：**

- 每个API接口绑定权限标识（如 `cliff:list`、`coffin:edit`）
- 权限标识与菜单的 `perms` 字段对应
- 超级管理员（SYS_ADMIN）默认拥有全部权限

### 8.3 数据加密

| 数据类型 | 加密方案 |
|---------|---------|
| 传输加密 | 全站HTTPS/TLS 1.3 |
| 密码 | bcrypt/argon2id 单向哈希 |
| 手机号 | AES-256-GCM 加密存储，脱敏显示（138****0001） |
| 邮箱 | AES-256-GCM 加密存储 |
| 数据库连接 | SSL加密 |
| 对象存储 | 服务端加密（SSE-S3/SSE-KMS） |
| 备份文件 | AES-256加密 |

### 8.4 审计日志

**操作日志记录范围：**

- 所有写操作（新增/编辑/删除/发布/导出）
- 登录/退出/密码修改
- 权限变更
- 敏感数据访问（如查看完整手机号）

**日志字段脱敏：**

- IP地址：完整记录（用于安全审计）
- 操作详情：不记录密码等敏感字段值

**日志保留策略：**

| 日志类型 | 保留期限 |
|---------|---------|
| 操作日志 | 3年（符合文物保护管理要求） |
| 登录日志 | 1年 |
| 在线用户 | 实时（会话结束即清除） |

### 8.5 文件上传安全

| 安全措施 | 实现方案 |
|---------|---------|
| 文件类型白名单 | 按资源类型限制扩展名（如模型仅 .glb/.gltf） |
| 文件大小限制 | 单文件最大500MB（三维模型），图片最大20MB |
| 文件内容检测 | 图片：验证图片头信息；模型：验证GLB二进制头 |
| 文件名消毒 | 去除路径分隔符、特殊字符，使用UUID重命名存储 |
| 存储隔离 | 上传文件不存储在应用服务器，使用独立对象存储 |
| 防盗链 | 对象存储配置Referer白名单 + 签名URL |

### 8.6 敏感操作保护

| 操作 | 保护措施 |
|------|---------|
| 删除崖墓群 | 二次确认 + 操作日志 + 关联数据检查 |
| 删除石棺 | 二次确认 + 操作日志 + 关联资源检查 |
| 删除用户 | 逻辑删除（status=disabled），保留审计记录 |
| 批量删除 | 限制单次最大100条 + 二次确认 |
| 修改密码 | 需验证当前密码 + 新密码强度校验 |
| 强制下线 | 管理员权限 + 操作日志 |

### 8.7 数据备份与恢复

| 备份类型 | 频率 | 保留期限 |
|---------|------|---------|
| 全量备份 | 每日 | 30天 |
| 增量备份 | 每小时 | 7天 |
| 事务日志备份 | 每15分钟 | 3天 |
| 对象存储备份 | 每日 | 90天 |

### 8.8 合规要求

1. **个人信息保护**：遵循《个人信息保护法》，手机号、邮箱加密存储，提供数据导出和删除功能
2. **文物保护数据**：遵循《文物保护法》，文物台账数据不可物理删除，仅可逻辑标记
3. **网络安全等级保护**：建议按等保二级要求部署，包含访问控制、审计追踪、入侵防范
4. **数据出境**：本项目数据不出境，对象存储选择国内区域
