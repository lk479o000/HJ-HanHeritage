# 合江汉代画像石棺数字化保护与展示利用项目 — 技术架构深度分析报告

---

## 1. 架构总览与设计哲学

### 1.1 项目全景

本项目采用**双端分离**的原型架构，面向两类截然不同的用户群体：

| 维度 | 游客端（prototype/） | 管理后台（prototype-admin/） |
|------|----------------------|------------------------------|
| 用户角色 | 公众游客、文博爱好者 | 博物馆管理员、系统运维人员 |
| 核心诉求 | 沉浸式浏览、文物认知 | 数据管理、运营监控、权限管控 |
| 技术选型 | 纯静态 HTML/CSS/JS（ES5） | iframe 壳 + 静态子页面 |
| 视觉风格 | 国风文博（天青·玉绿·宣纸） | B端后台（深色侧栏·浅灰内容） |
| 页面数量 | 6 个独立页面 | 21 个页面（含壳页面） |

### 1.2 设计哲学

原型的设计哲学可概括为**"零构建、全表达、双风格"**：

- **零构建**：不依赖任何前端构建工具（Webpack/Vite/ESBuild），所有代码均为浏览器可直接运行的 HTML/CSS/JS。这一选择大幅降低了原型阶段的工程复杂度，使设计师与前端开发者可以在文件系统层面直接协作，无需配置构建流水线。
- **全表达**：在无框架约束下，通过精心设计的 CSS 变量体系、IIFE 模块封装、全局 Store 对象，实现了接近框架化项目的组件复用与状态管理能力。原型并非"粗糙线框"，而是具备完整交互逻辑的高保真原型。
- **双风格**：游客端与管理端采用完全不同的视觉语言。游客端追求"博物馆展陈"的沉浸感（天青渐变、云纹装饰、楷体标题），管理端追求"企业后台"的效率感（深色侧栏、数据卡片、表格表单）。两套设计系统在 CSS 变量层面完全隔离，互不干扰。

## 2. 游客端架构深度分析

### 2.1 页面结构

游客端共 6 个页面，形成以地图首页为入口的树状导航结构：

```
index.html（崖墓分布地图）
  ├── panorama.html（全景漫游）
  ├── coffin-map.html（石棺分布导览）
  │     └── coffin.html（石棺三维模型浏览）
  ├── cliff-detail.html?cliff=N（崖墓群专属页面 ×13）
  │     └── coffin.html?coffin=N&from=ear
  └── ear-tomb.html（大耳朵崖墓群特色页面）
        └── coffin.html?coffin=N&from=ear
```

页面间通过 URL 参数传递状态（`?cliff=5`、`?coffin=1&from=ear`），这是一种轻量但有效的页面间通信机制。`from=ear` 参数尤其巧妙——它让石棺页的"返回"按钮能动态指向来源页面（大耳朵崖墓群而非首页），实现了上下文感知的导航。

### 2.2 组件化分析

在无框架环境下，游客端通过以下策略实现组件化：

**数据组件**：[cliff-data.js](file:///Users/cole/GitHub/prototype/prototype/assets/cliff-data.js) 将 13 处崖墓标点数据封装为全局变量 `CLIFF_MARKERS_13`，通过 IIFE 挂载到 `window` 对象。数据与渲染分离，`home-map.js` 和 `cliff-detail.html` 均消费同一份数据源。

**渲染组件**：[home-map.js](file:///Users/cole/GitHub/prototype/prototype/assets/home-map.js) 负责将 `CLIFF_MARKERS_13` 渲染为地图标点按钮。每个标点是一个绝对定位的 `<button>` 元素，`left/top` 为百分比坐标，支持 `featured` 标记（大耳朵崖墓群使用六边形+鎏金边样式）。

**交互组件**：[app.js](file:///Users/cole/GitHub/prototype/prototype/assets/app.js) 提供 4 个通用交互模块：
- `initTabs()` — Tab 切换（基于 `data-tabs` 属性选择器）
- `initFullscreen()` — 全屏切换（Fullscreen API）
- `initBackgroundColor()` — 背景取色器
- `openHotspotDialog()` — 墓口热点弹窗（HTML `<dialog>` 元素）

**内联页面脚本**：coffin.html 和 panorama.html 的核心逻辑以 `<script>` 内联方式写在页面底部。这种选择在原型阶段是合理的——页面逻辑与页面 DOM 强耦合，无需跨页复用。

### 2.3 三维渲染架构

三维模型浏览基于 Google `<model-viewer>` Web Component（v3.5.0，jsDelivr CDN），这是整个游客端最核心的技术选型。

**加载策略**：

```html
<script type="module" src="https://cdn.jsdelivr.net/npm/@google/model-viewer@3.5.0/dist/model-viewer.min.js"></script>
```

`type="module"` 确保脚本异步加载，不阻塞页面渲染。model-viewer 内部使用懒加载和占位符机制，在模型下载期间显示加载进度。

**模型池机制**：coffin.html 使用 `MODEL_POOL` 数组轮换 4 个演示模型（Horse/RobotExpressive/Astronaut/NeilArmstrong），28 具石棺通过取模运算 `(n-1) % 4` 分配模型。这是典型的原型模拟策略——用有限资源覆盖大量数据条目。

**相机控制**：model-viewer 的相机通过 HTML 属性配置，核心参数包括：

| 属性 | 作用 | 值域 |
|------|------|------|
| `camera-orbit` | 相机轨道角 | 方位角·仰角·距离 |
| `camera-target` | 相机焦点 | xyz 坐标 |
| `field-of-view` | 视场角 | 30deg |
| `min-camera-orbit` | 最小仰角 | auto 45deg auto |
| `max-camera-orbit` | 最大仰角 | auto 98deg auto |

仰角限制在 45°-98° 之间，有效防止用户看到石棺底面——这是文博展陈的常见需求（展品底部通常无纹理或无意义）。

**尺寸测量**：石棺测量功能通过 `model-viewer` 的 `positionAndNormalFromPoint()` API 实现。用户在模型表面依次点击两点，计算三维空间欧氏距离。实现要点：
- 使用 `customElements.whenDefined()` 确保 Web Component 注册完成后再绑定事件
- 测量状态通过 `state.measureOn` 和 `state.measurePts` 管理
- 测量结果以"模型坐标单位"显示，明确标注"仅供参考"

**5 种展示模式**：石棺页支持三维模型、数字正射影像图、数字拓片图、数字线划图、数字信息增强图 5 种展示模式。模式切换通过 `setStageView()` 函数实现，核心逻辑是在 `<model-viewer>` 和 `<figure>` 之间切换显示，同时联动工具栏的显隐。

### 2.4 全景渲染架构

全景漫游基于 Pannellum（v2.5.6，jsDelivr CDN），支持两种全景类型：

**等距柱状投影（equirectangular）**：用于空中、地面、室外全景，配置项包括 `pitch`、`yaw`、`hfov`（水平视场角），支持 360°×180° 全视角浏览。

**局部全景（partial）**：用于室内场景，通过 `haov`（水平视角范围）、`vaov`（垂直视角范围）参数限定可视区域。室内场景使用项目自有素材（`pano-museum-indoor-hall.png`、`pano-museum-indoor-coffin.png`），非标准 360° 全景图，因此采用 partial 模式包装。

**场景管理**：panorama.html 的 `MUSEUM_SCENES` 对象按类型（air/ground/indoor/outdoor）组织 8 个场景，每个场景包含 `id`、`title`、`pano`（全景图 URL）、`thumb`（缩略图）、`view`/`partial`（视角参数）。场景切换时先 `destroy()` 当前 viewer 实例再重建，确保无内存泄漏。

**缩略图条**：底部缩略图条使用 `scroll-snap-type: x proximity` 实现水平滚动吸附，每个缩略图按钮包含图片和标题文字，当前场景通过 `aria-current="true"` 标识。

### 2.5 数据流分析

游客端的数据流极为简洁——**无状态、无持久化、纯渲染**：

```
cliff-data.js → window.CLIFF_MARKERS_13
                      ↓
         ┌────────────┼────────────┐
         ↓            ↓            ↓
    home-map.js   cliff-detail   coffin-map.js
    (渲染标点)    (读取标点数据)  (模拟28标点)
```

coffin.html 的数据完全由 `getData(n)` 函数在运行时生成——石棺名称、年代、出土地点、画像内容均通过编号取模计算得出。这种"算法生成数据"的策略在原型阶段非常高效，但生产环境必须替换为真实 API 数据。

## 3. 管理后台架构深度分析

### 3.1 iframe 壳架构

管理后台的核心架构是**iframe 壳模式**——一个持久化的壳页面（index.html）承载侧栏和顶栏，通过 iframe 加载各业务子页面。

**壳页面结构**：

```html
<div class="admin-root shell-root">
  <aside class="admin-sidebar" id="shell-sidebar"></aside>
  <div class="shell-main">
    <header class="admin-topbar" id="shell-topbar"></header>
    <iframe id="admin-iframe" src="dashboard.html?embed=1"></iframe>
  </div>
</div>
```

**嵌入检测机制**：[embed.js](file:///Users/cole/GitHub/prototype/prototype-admin/assets/embed.js) 是整个壳架构的关键纽带——当子页面检测到 URL 参数 `embed=1` 时，为 `<html>` 元素添加 `embed-mode` 类，CSS 规则随即隐藏子页面自带的侧栏和顶栏：

```css
html.embed-mode .admin-sidebar { display: none !important; }
html.embed-mode .admin-topbar { display: none !important; }
```

这一设计使得每个子页面都具备**双模运行能力**：独立访问时显示完整布局（侧栏+顶栏+内容），嵌入 iframe 时仅显示内容区。这种"渐进增强"的页面设计在原型阶段极具价值——开发者可以直接在浏览器中打开任意子页面进行调试，无需通过壳页面。

**导航机制**：壳页面的侧栏链接使用 `data-shell-href` 和 `data-shell-id` 自定义属性，点击时通过 JavaScript 拦截默认行为，改为设置 iframe 的 `src` 属性并更新 `sessionStorage` 中的 `adminShellActiveId`。sessionStorage 用于在壳页面刷新时恢复上次的活动菜单项。

### 3.2 布局引擎

[admin-layout.js](file:///Users/cole/GitHub/prototype/prototype-admin/assets/admin-layout.js) 是管理后台的布局引擎，约 420 行代码，承担以下职责：

**菜单树渲染**：`MENU_TREE` 数组定义了 6 组一级菜单（业务数据/组织与权限/日志与在线/运维监控/系统配置/账户），每组包含若干叶子节点。渲染函数 `renderMenuHtml()` 支持两种模式：
- `renderSidebar(activeId)` — 独立页面模式，链接直接指向 HTML 文件
- `renderShellSidebar(activeId)` — 壳模式，链接使用 `data-shell-href` 属性

**菜单折叠**：一级菜单组通过 `data-menu-toggle="l1"` 按钮控制展开/折叠，CSS 类 `is-open` 控制面板显隐。当前活动菜单所在的一级组默认展开（`leafMatchesActive()` 递归检测）。

**菜单覆盖机制**：`readMenuOverrideMap()` 从 localStorage 读取 SysConfigStore 中的菜单配置覆盖，支持：
- 隐藏菜单项（`status: "disabled"` → `hidden: true`）
- 重命名菜单项（`label` 覆盖）
- 排序菜单项（`sort` 覆盖，通过 `sortedMenuNodes()` 实现）

这一机制实现了**菜单管理页面与侧栏的实时联动**——管理员在"菜单管理"中修改排序或禁用某项后，侧栏会在下次渲染时反映变更。

**API 设计**：`AdminLayout` 全局对象暴露 5 个方法：

| 方法 | 用途 |
|------|------|
| `init(opts)` | 独立页面模式初始化 |
| `initShell(opts)` | 壳模式初始化 |
| `refreshShellNavigation()` | 刷新壳导航（菜单变更后调用） |
| `shellNavigate(href, activeId)` | 编程式导航 |
| `initTabs(root)` | 初始化 Tab 组件 |

### 3.3 Store 层架构

管理后台的数据层由 3 个 Store 模块构成，形成**持久化 + 内存**的混合存储架构：

#### SysConfigStore（localStorage 持久化）

[sys-config-store.js](file:///Users/cole/GitHub/prototype/prototype-admin/assets/sys-config-store.js) 约 568 行，是整个后台最复杂的模块。它管理三类数据：

**菜单树**：采用树形结构存储，每个节点包含 `id`、`name`、`icon`、`sort`、`perms`（权限标识）、`component`（路由组件路径）、`status`（normal/disabled）、`linkId`（关联叶子菜单 ID）、`children`。支持完整的 CRUD 操作：
- `getMenuTree()` — 获取完整菜单树
- `getMenuNode(id)` — 按 ID 查找节点
- `updateMenuNode(id, patch)` — 更新节点属性
- `addMenuNode(parentId, partial)` — 新增节点（ID 使用 `Date.now().toString(36)` + 随机字符串生成）
- `deleteMenuNode(id)` — 删除节点

**数据迁移**：`migrateMenuItemsToTree()` 函数处理从旧版扁平菜单格式到树形格式的迁移，`ensureShape()` 函数在每次读取时校验数据完整性并自动修复缺失字段。这种防御性编程确保了 localStorage 数据在不同原型版本间的兼容性。

**通知公告**：支持草稿/已发布双状态，包含 `scope` 可见性范围（all/dept/role），`contentHtml` 富文本内容。

**账户资料**：存储当前登录用户的 `account`、`displayName`、`phone`、`email`、`dept`、`roles` 信息。

#### OrgAdminStore（内存存储）

[org-store.js](file:///Users/cole/GitHub/prototype/prototype-admin/assets/org-store.js) 约 57 行，管理组织架构数据。采用内存存储的原因是组织数据需要在多个子页面间实时共享（用户-部门-角色-岗位联动），而 iframe 环境下 localStorage 的变更事件无法跨 iframe 传播。

数据结构：
- `depts` — 4 个部门（树形，parentId 关联）
- `roles` — 4 个角色（含 `dataScope` 数据权限范围和 `permissionIds` 权限项列表）
- `posts` — 3 个岗位（含 `permissionIds`）
- `users` — 3 个用户（关联 `deptId`、`roleIds`、`postIds`）
- `counters` — 自增 ID 计数器

#### LogMonitorStore（内存存储）

[log-monitor-store.js](file:///Users/cole/GitHub/prototype/prototype-admin/assets/log-monitor-store.js) 管理日志与在线数据，预置 10 条操作日志、8 条登录日志、4 个在线用户。支持 `appendOperation()` 和 `appendLogin()` 追加方法，模拟实时日志写入。

### 3.4 权限模型

权限模型由 [org-permissions.js](file:///Users/cole/GitHub/prototype/prototype-admin/assets/org-permissions.js) 定义 5 个权限项：

| ID | 权限项 | 说明 |
|----|--------|------|
| m1 | 系统管理 | 用户/角色/部门/岗位 |
| m2 | 崖墓与墓口台账 | 业务核心数据 |
| m3 | 石棺与文物资源 | 业务核心数据 |
| m4 | 多媒体与全景 | 媒体资源管理 |
| m5 | 日志与审计 | 只读权限 |

权限分配通过角色和岗位两个维度：
- 角色的 `permissionIds` 数组定义该角色拥有的权限集合
- 岗位的 `permissionIds` 数组定义该岗位的权限集合
- 用户的 `roleIds` 和 `postIds` 关联到角色和岗位

角色的 `dataScope` 字段定义数据可见范围（all=全部/dept=本部门），这是典型的 RBAC + 数据权限模型。

### 3.5 菜单-侧栏联动机制

菜单管理与侧栏的联动是管理后台最精巧的设计之一，其工作流程如下：

```
菜单管理页面操作
      ↓
SysConfigStore.updateMenuNode() → localStorage 写入
      ↓
AdminLayout.refreshShellNavigation() 被调用
      ↓
readMenuOverrideMap() 从 localStorage 读取覆盖映射
      ↓
renderShellSidebar() 重新渲染侧栏 HTML
      ↓
sortedMenuNodes() 按 sort 字段排序
      ↓
renderLeaf() 检查 hidden 标记，过滤禁用菜单
      ↓
bindSidebarToggles() 重新绑定折叠事件
```

关键设计点：
1. **覆盖而非替换**：侧栏的基础菜单结构由 `MENU_TREE` 硬编码定义，SysConfigStore 的菜单树仅作为覆盖层。`renderLeaf()` 先检查覆盖映射中是否有 `hidden: true`，有则不渲染该菜单项。
2. **排序优先级**：有 sort 覆盖的菜单项优先排序（`sortKey` 返回覆盖值），无覆盖的按默认序号 50000+ 排序。
3. **实时性**：由于 iframe 子页面与壳页面共享同一 localStorage，子页面中的菜单修改可以立即反映到壳页面的侧栏——前提是调用 `refreshShellNavigation()`。但在当前实现中，子页面无法直接调用壳页面的 JavaScript 方法（跨 iframe 边界），因此刷新可能需要用户手动刷新壳页面。

## 4. 前端状态管理分析

### 4.1 localStorage 持久化策略

SysConfigStore 使用 localStorage 作为持久化存储，key 为 `prototypeAdminSysConfigV1`。其策略特点：

**读写模式**：每次操作都是"读-改-写"三步——`getState()` 从 localStorage 读取并解析 JSON，修改内存对象后 `saveRaw()` 序列化回写。这种模式简单直接，但存在性能隐患：频繁的 JSON.parse/JSON.stringify 在数据量大时可能造成卡顿。

**数据完整性**：`ensureShape()` 函数在每次 `getState()` 时执行，确保数据结构完整。它处理三种场景：
1. 无数据 → 使用默认值初始化
2. 旧版扁平菜单 → 迁移为树形结构
3. 字段缺失 → 用默认值补全

**容量限制**：localStorage 通常限制为 5MB。当前数据量远未触及上限，但菜单树如果无限增长可能成为问题。`pruneRemovedMenuNodes()` 函数会清理已废弃的菜单节点（如 `mon-sys`、`sys-integration`），防止数据膨胀。

**错误处理**：所有 localStorage 操作都包裹在 try-catch 中，确保在隐私模式或存储已满时不会崩溃。但错误被静默吞没（`catch(e){}`），生产环境应增加用户提示。

### 4.2 内存 Store 共享机制

OrgAdminStore 和 LogMonitorStore 采用 `window` 全局对象挂载，并通过**单例守卫**防止重复初始化：

```javascript
if (window.OrgAdminStore) return;
window.OrgAdminStore = { ... };
```

这一模式在 iframe 环境下有一个关键特性：每个 iframe 拥有独立的 `window` 对象，因此每个子页面加载 org-store.js 时都会创建自己的 Store 实例。这意味着：
- 在"用户管理"页面新增的用户，不会出现在"角色管理"页面的用户列表中
- 操作日志的追加仅影响当前页面的 Store 实例

这是原型阶段的一个已知限制。生产环境通过后端 API 天然解决了这一问题——所有页面共享同一数据库。

### 4.3 数据一致性保障

当前原型的数据一致性保障机制较为薄弱：

| 场景 | 当前行为 | 生产环境方案 |
|------|----------|-------------|
| 跨 iframe 数据同步 | 不同步 | 后端 API + WebSocket |
| localStorage 并发写入 | 后写覆盖 | 乐观锁/版本号 |
| 页面刷新后数据恢复 | SysConfigStore 可恢复，OrgAdminStore 丢失 | 全部走后端 API |
| 多标签页数据冲突 | 无处理 | BroadcastChannel / SW |

SysConfigStore 的数据在页面刷新后可以恢复（localStorage 持久化），但 OrgAdminStore 的数据在刷新后会重置为初始值（内存存储）。这意味着在原型演示时，组织架构的修改是"一次性"的——刷新即丢失。

## 7. 从原型到生产的技术演进路线

### 7.1 Vue3 迁移策略

**迁移原则**：渐进式迁移，优先迁移管理后台，游客端可延后。

**Phase 1 — 管理后台 Vue3 化**：

当前管理后台的 iframe 壳架构可直接映射为 Vue3 的布局组件：

```
当前架构                          Vue3 架构
index.html (壳)          →      App.vue (Layout)
  ├ sidebar               →        ├ Sidebar.vue
  ├ topbar                →        ├ Topbar.vue
  └ iframe → 子页面       →        └ <router-view> → 各页面组件
```

Vue Router 替代 iframe 导航，Pinia 替代全局 Store 对象。迁移步骤：
1. 使用 Vite 创建 Vue3 项目
2. 将 admin-layout.js 的菜单树数据迁移为路由配置
3. 将 SysConfigStore 迁移为 Pinia Store（保留 localStorage 持久化插件）
4. 将 OrgAdminStore 迁移为 Pinia Store（对接后端 API）
5. 逐页面迁移：每个 HTML 页面 → Vue SFC 组件

**Phase 2 — 游客端 Vue3 化**：

游客端迁移优先级较低，因为：
- 页面数量少（6 个）
- 交互逻辑相对简单
- SEO 需求可能需要 SSR（Nuxt3）

如果需要 SEO，建议使用 Nuxt3 框架，利用其 SSR 能力确保搜索引擎可索引。

### 7.2 管理后台 UI 框架选择

**推荐方案：Vue Element Admin + Element Plus**

**选择理由**：

1. **风格一致性**：现有原型的后台设计（深色侧栏 `#1a2332`、主色调蓝色 `#2563eb`、圆角 `10px`）与 Element Plus 的设计语言高度一致，迁移后能最大程度保持与 Demo 的视觉一致性。

2. **组件匹配度**：原型中的表格、表单、树形菜单、卡片等组件均可直接映射为 Element Plus 组件：
   - 表格 → `el-table`
   - 表单 → `el-form` + `el-input`
   - 树形菜单 → `el-tree`
   - 卡片 → `el-card`
   - 分页 → `el-pagination`

3. **成熟度与生态**：Vue Element Admin 是国内最成熟的 Vue 后台框架，文档完善，社区活跃，二开案例丰富。

4. **甲方验收保障**：保持与 Demo 风格一致，降低甲方验收时的沟通成本。

**主题定制**：参考原型的国风设计系统，通过 Element Plus 的主题变量覆盖实现定制：
- 主色调：`--el-color-primary: #6aada0`（玉绿）
- 侧栏背景：`--admin-sidebar-bg: #1a2332`
- 内容区背景：`--admin-main-bg: #f1f5f9`

**备选方案对比**：

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **Vue Element Admin** | 风格匹配、成熟稳定、迁移成本低 | 稍显传统 | 本项目首选 |
| **Vue Vben Admin** | 更现代、TypeScript原生 | 组件库为Ant Design Vue，风格差异大 | 需要重定制时考虑 |
| **Naive UI** | 轻量现代、高度灵活 | 需要自建布局框架 | 小型项目 |

## 8. 关键技术决策与权衡

### 8.1 iframe 壳 vs SPA

**选择**：iframe 壳架构

**优势**：
- 每个子页面完全独立，修改一个页面不影响其他页面
- 子页面可独立调试，直接在浏览器打开即可
- 天然实现了 JS/CSS 隔离，避免样式冲突
- 与传统后端渲染项目（如若依/RuoYi）的架构一致，团队迁移成本低

**劣势**：
- 跨 iframe 通信困难（postMessage 机制复杂）
- 每次导航重新加载完整页面，体验不如 SPA 流畅
- 全局状态无法自然共享
- 内存占用较高（每个 iframe 独立运行时）

**评估**：在原型阶段，iframe 壳是正确的选择——它最大化了开发效率和调试便利性。生产环境应迁移为 SPA（Vue3 + Vue Router），但保留子页面独立调试的能力（开发模式下可独立访问）。

### 8.2 model-viewer vs Three.js

**选择**：Google `<model-viewer>`

**优势**：
- 零代码三维展示：HTML 属性声明式配置，无需编写 WebGL 代码
- 内置 AR 支持（WebXR）
- 内置加载进度、错误处理、无障碍标签
- 自动处理模型加载、渲染、交互
- 体积相对 Three.js 更小

**劣势**：
- 定制能力有限：无法自定义着色器、后处理效果
- 不支持多模型场景（无法同时展示崖墓+石棺的组合场景）
- 测量功能需要通过 API 间接实现，不如 Three.js 直接操作几何体灵活
- 性能优化空间有限（无法控制渲染循环、LOD 等）

**评估**：对于"单模型浏览+测量"的场景，model-viewer 是最优选择。如果未来需要"崖墓群实景三维漫游"（多模型、碰撞检测、路径导航），则需要引入 Three.js。

### 8.3 localStorage vs 后端 API

**选择**：localStorage（原型阶段）

**优势**：
- 零后端依赖，原型可完全离线运行
- 读写延迟极低（本地操作）
- 实现简单，无需处理网络错误

**劣势**：
- 5MB 容量限制
- 无并发控制
- 无加密，数据明文存储
- 无法跨设备/跨浏览器同步
- 刷新后 OrgAdminStore 数据丢失

**评估**：原型阶段使用 localStorage 是合理的——它让前端开发者可以在无后端的情况下完成全部交互逻辑。生产环境必须替换为后端 API，localStorage 仅保留 Token 和用户偏好等少量数据。

### 8.4 ES5 vs TypeScript

**选择**：ES5（无构建步骤）

**优势**：
- 浏览器直接运行，无需编译
- 学习成本低，团队任何人都能修改
- 无需配置 tsconfig、构建工具

**劣势**：
- 无类型检查，重构风险高
- 无 IDE 智能提示，开发效率低
- 无法使用 ES6+ 特性（解构、箭头函数、async/await 等）
- 代码冗长（`function` 关键字、`var` 声明、手动 `forEach`）

**评估**：原型阶段使用 ES5 是务实的选择。但代码中已经出现了 ES6 的痕迹——`model-viewer` 使用 `type="module"` 加载，`customElements.whenDefined()` 返回 Promise。生产环境应全面迁移至 TypeScript，利用类型系统保障代码质量。

## 9. 架构优化建议

### 9.1 短期优化（1-2 周）

**S1. 统一 escapeHtml 工具函数**

将分散在 6+ 个文件中的 `escapeHtml()` 抽取为独立的 `utils.js` 模块，所有页面统一引用。同时补充单引号转义（当前部分实现缺少 `'` → `&#39;`）。

**S2. 内联脚本外置**

将 coffin.html 和 panorama.html 的内联 `<script>` 迁移为独立的 JS 文件（coffin-viewer.js、panorama-viewer.js），便于维护和复用。

**S3. 添加 Service Worker 离线缓存**

为游客端添加 Service Worker，缓存 HTML/CSS/JS 和地图底图，确保博物馆内无网络环境下仍可正常浏览。

**S4. 图片优化**

将全景图和地图底图转换为 WebP 格式，添加 `loading="lazy"` 和 `decoding="async"` 属性（部分已实现）。

### 9.2 中期优化（1-3 月）

**M1. 管理后台 Vue3 化**

按照 7.1 节的迁移策略，将管理后台迁移为 Vue3 + Vite + Pinia + Vue Router 项目。优先迁移布局引擎和 Store 层，再逐页面迁移。

**M2. 后端 API 搭建**

基于 Spring Boot 3.x 搭建后端服务，优先实现：
- 认证授权（JWT）
- 崖墓/石棺 CRUD API
- 文件上传（三维模型、全景图）
- 组织架构 API

**M3. 数据库设计与部署**

按照 7.3 节的方案设计数据库，使用 Flyway 管理数据库迁移。

**M4. 三维模型替换**

将 model-viewer 的演示模型替换为真实的石棺 GLB 模型。需要：
- 建立模型制作规范（面数限制、纹理尺寸、坐标系）
- 实现模型上传和转码流水线
- 添加模型加载进度指示器

### 9.3 长期优化（3-6 月）

**L1. 游客端 Vue3/Nuxt3 化**

使用 Nuxt3 重构游客端，实现 SSR 以支持 SEO。关键页面（崖墓详情、石棺详情）需要搜索引擎可索引。

**L2. Three.js 高级场景**

对于"崖墓群实景三维漫游"需求，引入 Three.js 实现：
- 多模型场景管理
- 碰撞检测与路径导航
- 自定义着色器（石棺画像高亮、风化效果模拟）
- LOD（Level of Detail）优化远距离渲染

**L3. 全景漫游升级**

从 Pannellum 升级为基于 Three.js 的全景方案，支持：
- 多场景热点跳转
- 全景内嵌三维模型（在全景中放置石棺模型）
- VR 模式（WebXR）

**L4. 运维监控对接**

将管理后台的模拟监控数据替换为真实监控：
- JVM 监控：Spring Boot Actuator + Micrometer
- Redis 监控：Spring Data Redis + Lettuce
- 服务器监控：Prometheus + Grafana
- 日志收集：ELK Stack（Elasticsearch + Logstash + Kibana）

**L5. CI/CD 流水线**

建立完整的持续集成/持续部署流水线：
- 代码提交 → ESLint + TypeScript 类型检查
- PR 合并 → 自动化测试 + 预览环境部署
- Release → 生产环境部署 + 数据库迁移
