## 二、前端性能优化方案

### 2.1 三维模型加载优化

本项目核心挑战之一是 **28 具石棺的三维模型浏览**，单个 GLB 文件可达 50~200MB。

#### 2.1.1 模型预处理管线

```
原始高精度模型 (.obj/.fbx, 500MB~2GB)
        │
        ▼
  ┌─────────────┐
  │ MeshLab/Blender │  ← 减面优化
  │  多边形简化     │     目标：三角面 < 50万
  │  UV 合并       │     法线平滑
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │ glTF-Pipeline │  ← 格式转换与压缩
  │  Draco 压缩   │     mesh compression: enabled
  │  纹理压缩      │     texture KTX2 + BasisU
  │  动画烘焙      │
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │  输出多级LOD  │  ← 生成多精度版本
  │  LOD-0: 完整版 │     50~150MB（桌面端）
  │  LOD-1: 中等版 │     15~40MB（平板端）
  │  LOD-2: 轻量版 │     5~15MB（移动端）
  └─────────────┘
```

**具体优化措施：**

| 优化项 | 工具/方法 | 效果预估 |
|--------|----------|---------|
| Draco 几何压缩 | gltfpipeline `-d` | 模型体积减少 70%~90% |
| 纹理压缩（KTX2+BasisU） | gltfpipeline `-t ktx2` | 纹理体积减少 60%~80% |
| 多边形简化（目标 < 50万面） | Blender Decimate Modifier | 保持视觉效果前提下体积减半 |
| 合并材质球 | Blender 材质合并 | 减少 draw call |
| 移除冗余顶点属性 | gltfpipeline 清理 | 减少 10%~20% |
| 生成 `.glb` 二进制格式 | gltfpipeline `-i` | 比 gltf+bin 小 10%~15% |

#### 2.1.2 运行时加载优化

**关键优化策略：**

**1. 设备自适应 LOD 选择**

根据用户设备类型和网络状况自动选择合适的模型精度：
- 移动端或 3G/2G 网络 → LOD-2（5~15MB）
- 移动端 4G 网络 → LOD-1（15~40MB）
- 桌面端 WiFi/有线 → LOD-0（50~150MB）

**2. 预加载下一具石棺模型**

用户浏览当前石棺时，后台静默预加载相邻石棺模型。利用 `<link rel="prefetch">` 或 `fetch()` 在空闲时段加载，不阻塞当前页面交互。

**3. 进度反馈 + 取消机制**

模型加载时显示进度条，用户切换石棺时取消上一个未完成的加载请求（AbortController），避免无效带宽浪费。

**4. model-viewer 优化配置**

```html
<model-viewer
  src="/models/coffin-${coffinId}-lod${currentLod}.glb"
  loading="eager"
  reveal="auto"
  auto-rotate
  camera-controls
  camera-orbit="45deg 55deg 105%"
  field-of-view="30deg"
  max-field-of-view="45deg"
  min-camera-orbit="auto auto 50%"
  max-camera-orbit="auto auto 200%"
/>
```

### 2.2 全景图片加载优化

全景图片（等距柱状投影）单张可达 20~100MB，Pannellum 渲染需特别注意。

#### 2.2.1 图片分级策略

```
原始全景图 (8000×4000 ~ 16000×8000px, 50~100MB)
        │
        ├── Level-0: 16384×8192 (完整版, 桌面端 WiFi)
        ├── Level-1: 8192×4096  (标准版, 平板/4G)
        ├── Level-2: 4096×2048  (轻量版, 手机/3G)
        └── Level-3: 2048×1024  (预览缩略图, 快速占位)
```

#### 2.2.2 全景加载优化措施

| 优化项 | 方法 | 效果 |
|--------|------|------|
| **渐进式加载** | 先显示低分辨率预览图，再逐步加载高清切片 | 首屏 < 1s 可见内容 |
| **立方体贴图转换** | equirectangular → cubemap 切片加载 | 减少首屏加载数据量 75% |
| **WebP 格式替代 JPG** | 全景图导出为 WebP（支持有损/无损） | 体积减少 30%~50% |
| **懒加载非当前视点** | 当前全景加载完成后才预加载同类型其他视点 | 减少初始带宽压力 |
| **缓存策略** | Service Worker 缓存已浏览过的全景 | 回访秒开 |
| **压缩感知** | 使用 Sharp/ImageMagick 在上传时自动生成多级分辨率 | 存储空间节省 60% |

#### 2.2.3 Pannellum 多分辨率配置

#### 4.1.3 流式输出优化

- Nginx 关闭 proxy_buffering，实现真正的流式透传
- 客户端断开检测，及时释放上游连接

| **分段策略** | 文物知识按「主题段落」分段（而非固定 token 数） | 上下文更完整 |
| **元数据过滤** | 检索时限定石棺编号/纹饰类型/年代范围 | 减少无关噪声 |
| **Rerank 重排序** | Cross-Encoder 精排（bge-reranker-v2-m3） | Top-5 精确率提升 10%~20% |
| **结果缓存** | 相似问题（余弦度 > 0.95）复用缓存回答 | 重复问题延迟降低 90% |
| **预计算 Embedding** | 知识库变更时增量更新向量 | 实时检索无额外编码开销 |

#### 6.1.2 MySQL 备份脚本

```bash
#!/bin/bash
# mysql-backup.sh — 每日全量备份

BACKUP_DIR="/data/backup/mysql"
DATE=$(date +%Y%m%d_%H%M%S)
RETENTION_DAYS=30

# 全量备份（xtrabackup，不锁表）
xtrabackup --backup \
  --target-dir=${BACKUP_DIR}/full_${DATE} \
  --user=backup_user \
  --password=${BACKUP_PASSWORD} \
  --compress \
  --compress-threads=4 \
  --parallel=4

# 备份校验
xtrabackup --prepare --target-dir=${BACKUP_DIR}/full_${DATE}

# 上传至异地 OSS
ossutil cp ${BACKUP_DIR}/full_${DATE} oss://hejiang-backup/mysql/full_${DATE} -r --force

# 清理本地过期备份
find ${BACKUP_DIR} -name "full_*" -mtime +${RETENTION_DAYS} -exec rm -rf {} \;

echo "[$DATE] MySQL full backup completed"
```

```yaml
      - uses: actions/download-artifact@v4
```

#### 8.3.2 部署流程

```

  ↓
```

### 8.4 灰度发布

#### 8.4.1 灰度策略

| 阶段 | 流量比例 | 持续时间 | 观察指标 | 回滚条件 |
|------|---------|---------|---------|---------|
| 内部测试 | 0%（仅内部 IP） | 1 天 | 功能正确性 | 功能异常 |
| 灰度 10% | 10% | 4 小时 | 错误率、延迟 | 5xx > 1%，P99 延迟翻倍 |
| 灰度 50% | 50% | 4 小时 | 错误率、延迟、业务指标 | 同上 |
| 全量发布 | 100% | 持续观察 | 全部指标 | 同上 |

#### 8.4.2 AI 功能灰度

AI 功能采用**功能开关（Feature Flag）**控制灰度：

| AI 功能 | 灰度策略 | 全量条件 |
|---------|---------|---------|
| AI 问答浮窗 | 先对内部用户开放 → 10% 游客 → 全量 | 满意度 > 85%，幻觉率 < 5% |
| AI 图像识别 | 先管理员可用 → 全部用户 | 识别准确率 > 90% |
| AI 辅助录入 | 先管理员可用 → 全部用户 | 自动填充准确率 > 80% |
| AI 智能搜索 | 先管理员可用 → 全部用户 | 搜索结果相关性 > 85% |

### 8.5 回滚方案

| 场景 | 回滚方式 | 操作时间 | 数据处理 |
|------|---------|---------|---------|
| 前端发布异常 | Nginx 切换旧版本静态资源 | < 1min | 无需处理 |
| 后端发布异常 | Docker 镜像回退到上一版本 | < 3min | 无需处理 |
| 数据库 Schema 变更异常 | Flyway undo migration | < 5min | 需评估数据兼容性 |
| AI Prompt 变更导致质量下降 | Prompt 版本回退 | < 1min | 无需处理 |
| 全局故障 | 全量回退到上一个稳定版本 | < 5min | 需评估数据兼容性 |

**回滚决策流程：**

1. 监控告警触发 → 值班人员确认影响范围
2. P0/P1 级故障 → 立即回滚（无需审批）
3. P2/P3 级故障 → 评估后决定回滚或热修复
4. 回滚后 → 保留现场日志，事后复盘

### 10.2 故障处理 SOP

#### 10.2.1 故障分级与响应

| 故障级别 | 定义 | 响应时间 | 处理时限 | 升级条件 |
|---------|------|---------|---------|---------|
| **P0** | 核心功能不可用（游客端/管理后台无法访问） | 5min | 30min | 15min 未恢复升级至技术总监 |
| **P1** | 重要功能异常（三维模型无法加载、AI 服务不可用） | 15min | 2h | 1h 未恢复升级至 P0 |
| **P2** | 一般功能异常（导出失败、缓存命中率低） | 1h | 8h | 4h 未恢复升级至 P1 |
| **P3** | 轻微问题（UI 显示异常、非核心功能报错） | 4h | 24h | — |

#### 10.2.2 常见故障处理 SOP

**SOP-01：服务不可用**

```
1. 确认影响范围（游客端/管理端/全部）
2. 检查 Nginx 状态：systemctl status nginx
3. 检查后端服务：curl http://localhost:8080/actuator/health
4. 检查数据库连接：mysql -e "SELECT 1"
5. 检查 Redis 连接：redis-cli ping
6. 如后端不可用 → 重启服务：docker-compose restart business-service
7. 如数据库不可用 → 切换从库：修改数据源配置指向从库
8. 如 5min 内未恢复 → 执行回滚到上一版本
9. 记录故障时间线和处理过程
```

**SOP-02：数据库性能骤降**

```
1. 检查慢查询：pt-query-digest /var/log/mysql/slow.log
2. 检查连接数：SHOW PROCESSLIST
3. 检查锁等待：SELECT * FROM information_schema.INNODB_LOCK_WAITS
4. Kill 长事务：KILL <thread_id>
5. 如为全表扫描 → 检查索引是否缺失
6. 如为连接池耗尽 → 临时增加 max_connections
7. 如为主从延迟 → 检查 binlog 同步状态
```

**SOP-03：AI 服务异常**

```
1. 检查 LLM 网关健康：curl http://llm-gateway:9000/health
2. 检查上游模型 API 可达性
3. 如主模型不可用 → 检查 ModelRouter 是否自动切换到备选模型
4. 如 Token 超限 → 检查日消耗量，必要时临时增加预算
5. 如 GPU 节点异常 → 检查 nvidia-smi，必要时重启 GPU 服务
6. 如向量检索异常 → 检查 Milvus 状态，必要时重建索引
```

**SOP-04：大文件上传失败**

```
1. 检查 MinIO 状态：mc admin info minio
2. 检查磁盘空间：df -h /data
3. 检查文件大小是否超限
4. 检查网络超时配置（Nginx proxy_read_timeout）
5. 如为分片合并失败 → 检查分片完整性，手动触发合并
6. 如为秒传误判 → 检查 MD5 计算逻辑
```
