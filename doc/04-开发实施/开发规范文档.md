## 1. 引言

### 1.1 文档目的

本文档为合江汉代画像石棺数字化保护与展示利用项目的开发规范文档，定义代码编写规范、Git工作流程、代码审查标准、文档编写规范和安全规范。本文档是开发团队必须遵守的准则，旨在保证代码质量、提高协作效率、减少潜在问题。

### 1.2 适用范围

本文档适用于本项目的所有开发人员，包括前端开发工程师和后端开发工程师。所有提交到代码仓库的代码必须符合本文档定义的规范。

### 1.3 规范原则

开发规范遵循以下原则。

可读性原则要求代码易于阅读和理解，变量命名清晰，注释准确完整，代码结构层次分明。可维护性原则要求代码易于维护和扩展，模块边界清晰，耦合度低，函数职责单一。一致性原则要求代码风格统一，整个项目使用相同的命名规则、缩进格式、注释风格。效率优先原则要求在保证可读性和可维护性的前提下，优化代码性能，避免不必要的计算和资源消耗。

## 2. 代码规范

### 2.1 通用规范

#### 2.1.1 命名规范

变量命名使用有意义的英文单词或词组，避免使用单个字母（循环变量除外）或无意义的名称。变量名采用驼峰命名法（camelCase），如userName、totalCount、isDeleted。类名采用帕斯卡命名法（PascalCase），如UserService、OrderController。函数名采用动词或动词短语，如getUserById、createOrder、validateInput。常量名使用全大写字母，单词间用下划线分隔，如MAX_RETRY_COUNT、DEFAULT_PAGE_SIZE。数据库表名和字段名使用小写字母，单词间用下划线分隔，如sys_user、create_time。

#### 2.1.2 缩进和格式

代码缩进使用4个空格，禁止使用Tab字符。代码行长度建议不超过120个字符，超过时需换行对齐。大括号使用K&R风格，即左大括号不单独占一行，右大括号单独占一行。

#### 2.1.3 注释规范

代码注释应清晰说明代码意图，而不是简单重复代码内容。注释使用中文编写，保持与代码同步更新。重要逻辑、复杂算法、业务规则必须添加注释。TODO注释使用统一格式，标注TODO内容和负责人。

### 2.2 前端代码规范

#### 2.2.1 Vue3规范

组件文件使用Vue3 Composition API编写，禁止使用Vue2 Options API。新组件采用script setup语法糖，简化代码编写。组件名称采用帕斯卡命名法，文件名采用帕斯卡命名法。组件Props定义需指定类型和默认值，使用TypeScript类型系统。

```typescript
// 正确的Props定义
interface Props {
  title: string
  count?: number
  type?: 'primary' | 'success' | 'danger'
}

const props = withDefaults(defineProps<Props>(), {
  count: 0,
  type: 'primary'
})

// 错误的Props定义
const props = defineProps({
  title: String,
  count: Number,
  type: String
})
```

组件结构按照以下顺序组织，template、script setup、style。样式使用Scoped CSS，避免样式污染全局。

#### 2.2.2 TypeScript规范

使用TypeScript进行类型检查，禁止使用any类型。接口和类型定义使用interface声明。枚举值使用const enum或enum声明。函数参数和返回值必须指定类型。

```typescript
// 正确的类型定义
interface UserInfo {
  id: number
  name: string
  email: string
  roles: string[]
}

function getUserById(id: number): Promise<UserInfo> {
  return request.get(`/users/${id}`)
}

// 错误的类型定义
function getUserById(id: any): any {
  return request.get(`/users/${id}`)
}
```

#### 2.2.3 CSS规范

样式变量定义在variables.scss中，统一管理颜色、字体、间距等设计令牌。样式使用BEM命名规范，如.block__element--modifier。禁止使用行内样式（特殊情况除外）。媒体查询统一在文件底部集中编写。

### 2.3 后端代码规范

#### 2.3.1 Java规范

类名使用帕斯卡命名法，如UserService、OrderController。方法名使用驼峰命名法，如getUserById、createOrder。成员变量使用驼峰命名法，私有成员变量可使用下划线前缀。静态常量使用全大写下划线分隔命名。

```java
// 正确的命名
public class UserService {
    private static final Logger logger = LoggerFactory.getLogger(UserService.class);
    private final UserMapper userMapper;
    
    public User getUserById(Long id) {
        return userMapper.selectById(id);
    }
}

// 错误的命名
public class userService {
    Logger log = LoggerFactory.getLogger(userService.class);
    
    public User getUserById(long ID) {
        return userMapper.SelectById(ID);
    }
}
```

#### 2.3.2 Node.js/TypeScript规范

使用NestJS框架进行后端开发。控制器命名使用帕斯卡命名法+Controller后缀，如UserController。服务类命名使用帕斯卡命名法+Service后缀。模块命名使用帕斯卡命名法+Module后缀。实体和DTO命名使用帕斯卡命名法。

```typescript
// 正确的命名
@Controller('users')
export class UserController {
  constructor(private readonly userService: UserService) {}
  
  @Get(':id')
  async getUserById(@Param('id') id: string): Promise<User> {
    return this.userService.getUserById(id)
  }
}

// 错误的命名
@Controller('User')
export class user_controller {
  constructor(private userService: user_service) {}
}
```

#### 2.3.3 数据库操作规范

使用ORM框架进行数据库操作，禁止直接编写SQL语句（复杂查询除外）。SQL语句需经过安全校验，防止SQL注入。数据库事务需明确标注，事务边界要清晰。敏感数据在数据库中加密存储。

### 2.4 API设计规范

#### 2.4.1 RESTful规范

接口路径使用资源名词复数形式，如/api/users表示用户资源。接口路径使用小写字母和下划线。HTTP方法表示操作语义，GET查询、POST新增、PUT更新、DELETE删除。

#### 2.4.2 接口文档

使用Swagger/OpenAPI注解编写接口文档。注解包括接口路径、请求方法、参数说明、响应说明等。文档需保持与代码同步更新。

```java
// Java Swagger注解示例
@Api(tags = "用户管理")
@RestController
@RequestMapping("/users")
public class UserController {
    
    @ApiOperation("根据ID查询用户")
    @ApiImplicitParam(name = "id", value = "用户ID", required = true)
    @GetMapping("/{id}")
    public User getUserById(@PathVariable Long id) {
        return userService.getUserById(id);
    }
}
```

### 2.5 测试代码规范

#### 2.5.1 测试文件组织

测试文件与源代码文件放在同一目录，使用相同文件名后加.test或.spec后缀。测试文件组织结构与源代码保持一致。

#### 2.5.2 测试用例命名

测试函数命名采用描述性名称，说明测试的场景和预期结果。使用given-when-then格式组织测试代码。

```typescript
// 正确的测试命名
describe('UserService', () => {
  it('should return user when user exists', async () => {
    // given
    const userId = 1
    const mockUser = { id: 1, name: '张三' }
    
    // when
    const result = await userService.getUserById(userId)
    
    // then
    expect(result).toEqual(mockUser)
  })
})
```

## 3. Git工作流

### 3.1 分支策略

#### 3.1.1 分支类型

主分支包括以下两种。main分支为主分支，始终保持与生产环境一致，不能直接在main分支上修改代码。develop分支为开发分支，包含下一版本即将发布的所有功能。所有功能开发完成后合并到main分支。

辅助分支包括以下几种。feature分支用于开发新功能，从develop分支创建，开发完成后合并回develop分支。命名格式为feature/功能名称，如feature/user-login。release分支用于版本发布准备，从develop分支创建，用于修复发布前的问题，测试通过后合并到main分支和develop分支。命名格式为release/v版本号，如release/v1.0.0。hotfix分支用于紧急修复生产环境问题，从main分支创建，修复完成后合并到main分支和develop分支。命名格式为hotfix/问题描述，如hotfix/fix-login-bug。

#### 3.1.2 分支命名规范

分支名称使用小写字母和连字符。feature分支命名为feature/功能名称，如feature/user-authentication。bugfix分支命名为fix/问题描述，如fix/login-validation。hotfix分支命名为hotfix/问题描述，如hotfix/security-patch。refactor分支命名为refactor/模块名称，如refactor/user-service。

### 3.2 提交规范

#### 3.2.1 提交信息格式

提交信息采用以下格式。

```
<类型>(<范围>): <简短描述>

[可选的正文]

[可选的页脚]
```

提交类型包括以下几种。feat表示新增功能。fix表示修复bug。docs表示文档更新。style表示代码格式调整，不影响代码运行。refactor表示代码重构。perf表示性能优化。test表示测试相关。chore表示构建或辅助工具更新。

提交范围指本次提交影响的功能模块，如user、order、auth等。

简短描述不超过50个字符，描述本次提交的内容。使用中文编写，描述做了什么，而不是怎么做的。

```bash
# 正确的提交信息示例
feat(user): 添加用户登录功能

- 实现用户名密码登录
- 添加JWT Token生成
- 实现登录日志记录

# 错误的提交信息示例
修改代码
fix bug
update
```

#### 3.2.2 提交频率

代码应频繁提交，每次完成一个小的逻辑单元就提交。提交信息需准确描述提交内容，避免无意义的提交。提交前需确认代码可以正常编译和运行。

### 3.3 合并规范

#### 3.3.1 合并前检查

合并分支前需确保以下条件满足。目标分支的最新代码已合并到当前分支。相关测试已通过。代码冲突已解决。代码审查已通过。

#### 3.3.2 合并方式

使用rebase保持提交历史整洁。在功能分支开发过程中，定期从主分支拉取最新代码进行rebase。合并到主分支时使用merge commit，保留完整的提交历史。

```bash
# 定期从develop拉取最新代码
git fetch origin
git rebase origin/develop

# 合并到develop
git checkout develop
git merge --no-ff feature/user-login
```

### 3.4 Tag管理

#### 3.4.1 版本号规范

版本号采用语义化版本规范，格式为主版本号。次版本号。修订号。主版本号在有不兼容的API变更时递增。次版本号在新增功能且保持向后兼容时递增。修订号在修复bug且保持向后兼容时递增。

#### 3.4.2 Tag创建

每次发布版本时创建Tag。Tag命名格式为v版本号，如v1.0.0。Tag创建时需添加注释说明版本内容。

```bash
git tag -a v1.0.0 -m "正式版本v1.0.0"
git push origin v1.0.0
```

## 4. 代码审查

### 4.1 审查流程

#### 4.1.1 提交Pull Request

开发人员完成功能开发后，创建Pull Request请求合并到目标分支。Pull Request标题使用提交信息格式，描述本次合并的内容。Pull Request描述需包含以下内容。功能说明，描述新增或修改的功能。测试说明，描述如何测试新增或修改的功能。相关文档，列出相关的文档更新。

#### 4.1.2 审查人员

每个Pull Request至少需要一名审查人员通过。核心模块和敏感代码需要两名审查人员通过。审查人员由技术负责人指定或由开发人员邀请。

#### 4.1.3 审查内容

代码审查主要检查以下内容。代码逻辑是否正确实现业务需求。代码是否符合编码规范。代码是否存在潜在问题或风险。代码是否影响其他模块。测试覆盖是否充分。文档是否同步更新。

### 4.2 审查清单

#### 4.2.1 功能审查

功能审查包括以下检查项。代码是否完整实现需求中的功能点。边界条件和异常情况是否处理。输入参数是否校验。返回值是否合理。错误处理是否完善。

#### 4.2.2 代码质量审查

代码质量审查包括以下检查项。变量和函数命名是否清晰易懂。代码结构是否清晰，层次是否分明。是否有重复代码可以抽取。是否有不必要的复杂性。注释是否准确完整。

#### 4.2.3 安全审查

安全审查包括以下检查项。是否有SQL注入风险。是否有XSS攻击风险。是否有敏感信息泄露。权限控制是否正确。密码是否加密存储。API是否有访问限制。

#### 4.2.4 性能审查

性能审查包括以下检查项。是否有不必要的数据库查询。是否有大循环或深层递归。是否正确使用缓存。是否有内存泄漏风险。是否正确关闭资源。

### 4.3 审查意见处理

审查人员提出意见后，开发人员需及时处理。同意的意见需按要求修改代码。不同意的意见需与审查人员讨论，达成共识。讨论过程需记录在Pull Request评论中。

### 4.4 审查通过条件

Pull Request通过审查需满足以下条件。所有必改意见已处理并修改完成。至少一名审查人员approve。所有CI/CD检查通过。无未解决的代码冲突。

## 5. 文档规范

### 5.1 代码注释规范

#### 5.1.1 注释内容

文件头部注释包含文件名、功能描述、创建日期、作者信息。

```typescript
/**
 * 用户管理模块
 * 
 * 提供用户注册、登录、信息修改等功能
 * 
 * @author 张三
 * @date 2026-01-01
 */
```

类和接口注释包含类的功能描述、作者、日期。方法注释包含方法功能、参数说明、返回值说明、可能抛出的异常。

```typescript
/**
 * 根据用户ID获取用户信息
 * 
 * @param id 用户ID
 * @returns 用户信息，不存在返回null
 * @throws BusinessException 当用户ID格式不正确时抛出
 */
async getUserById(id: string): Promise<User | null>
```

复杂逻辑注释包含算法说明、业务规则解释、关键计算说明。

#### 5.1.2 注释要求

注释需与代码同步更新，过时的注释比没有注释更有害。注释应解释为什么这样做，而不是简单重复代码。删除无用的注释和废弃代码。

### 5.2 接口文档规范

#### 5.2.1 Swagger注解

后端接口使用Swagger注解编写文档。

```java
@Api(tags = "用户管理")
@RestController
@RequestMapping("/users")
public class UserController {
    
    @ApiOperation("查询用户列表")
    @ApiImplicitParams({
        @ApiImplicitParam(name = "page", value = "页码", dataType = "Integer"),
        @ApiImplicitParam(name = "pageSize", value = "每页数量", dataType = "Integer")
    })
    @ApiResponses({
        @ApiResponse(code = 200, message = "成功"),
        @ApiResponse(code = 401, message = "未授权"),
        @ApiResponse(code = 500, message = "服务器错误")
    })
    @GetMapping
    public PageResult<User> listUsers(
        @RequestParam(defaultValue = "1") Integer page,
        @RequestParam(defaultValue = "10") Integer pageSize
    ) {
        return userService.listUsers(page, pageSize);
    }
}
```

#### 5.2.2 文档维护

接口文档需与代码同步更新。删除已废弃的接口时同步删除文档。新增接口时添加完整文档。文档变更需在Pull Request中说明。

### 5.3 README文档规范

项目根目录需包含README.md文件，内容包括项目名称、项目简介、功能特性、技术架构、快速开始、部署说明、版本历史、联系方式。

模块目录可包含README.md文件，内容包括模块简介、功能列表、使用说明、注意事项。

## 6. 安全规范

### 6.1 敏感信息处理

#### 6.1.1 禁止硬编码

禁止在代码中硬编码敏感信息，包括密码、密钥、Token、数据库连接信息等。敏感信息存储在环境变量或配置中心。代码仓库中不能包含任何敏感信息的明文。

#### 6.1.2 密码处理

用户密码必须使用bcrypt或argon2等强哈希算法加密存储。密码在传输过程中必须加密（使用HTTPS）。密码在日志中不能明文记录。

#### 6.1.3 密钥管理

API密钥、数据库密码等使用专门的密钥管理服务存储。密钥定期轮换，过期密钥及时撤销。密钥泄漏后立即更换并排查影响范围。

### 6.2 输入安全

#### 6.2.1 参数校验

所有用户输入必须进行校验。使用框架提供的校验注解或校验方法。校验规则需在接口文档中说明。

```java
@PostMapping("/users")
public Result<User> createUser(@RequestBody @Valid CreateUserDTO dto) {
    // 参数校验由@Valid注解自动处理
    return userService.createUser(dto);
}
```

#### 6.2.2 SQL注入防护

使用参数化查询或ORM框架进行数据库操作。禁止拼接SQL字符串。LIKE查询需对特殊字符进行转义。

```java
// 正确：使用参数化查询
@Select("SELECT * FROM users WHERE name = #{name}")
List<User> findByName(@Param("name") String name);

// 错误：拼接SQL
@Select("SELECT * FROM users WHERE name = '" + name + "'")
List<User> findByName(String name);
```

#### 6.2.3 XSS防护

用户输入在输出到页面时进行HTML转义。富文本内容使用专门的XSS过滤器。禁止使用v-html指令渲染用户输入的HTML内容。

### 6.3 认证授权

#### 6.3.1 认证机制

使用JWT令牌进行身份认证。Token设置合理的过期时间，建议2小时。Token黑名单机制支持主动失效。

#### 6.3.2 权限控制

接口使用@PreAuthorize等注解进行权限控制。前端路由使用权限指令进行菜单控制。敏感操作需二次验证。

```java
@PreAuthorize("hasAuthority('system:user:delete')")
@DeleteMapping("/{id}")
public Result<Void> deleteUser(@PathVariable Long id) {
    return userService.deleteUser(id);
}
```

### 6.4 日志安全

#### 6.4.1 日志内容

日志中禁止记录敏感信息，包括密码、Token、身份证号、手机号等。日志需记录操作人、操作时间、操作内容、操作结果。异常日志需记录堆栈信息便于排查。

#### 6.4.2 日志存储

日志存储需满足合规要求。日志文件需设置合理的权限，禁止未授权访问。日志需定期归档和清理。

## 7. 配置规范

### 7.1 环境配置

#### 7.1.1 环境类型

项目环境分为以下几类。开发环境（dev）用于本地开发，配置宽松，安全要求较低。测试环境（test）用于测试团队测试，与开发环境隔离。预发布环境（staging）用于上线前验证，配置与生产一致。生产环境（prod）用于正式服务，配置最严格，安全要求最高。

#### 7.1.2 配置文件组织

使用多环境配置文件，如application-dev.yml、application-test.yml、application-prod.yml。公共配置放在application.yml中，环境相关配置放在对应环境的配置文件中。敏感配置使用环境变量覆盖。

### 7.2 环境变量

#### 7.2.1 变量命名

环境变量使用全大写字母，单词间用下划线分隔。变量名需具有描述性，如DATABASE_HOST、REDIS_PASSWORD。

#### 7.2.2 变量使用

在代码中使用process.env访问环境变量。提供默认值处理变量未配置的情况。敏感变量在文档中标注需保密。

### 7.3 依赖管理

#### 7.3.1 版本锁定

前端使用package-lock.json锁定依赖版本。后端使用pom.xml或package-lock.json锁定依赖版本。禁止在CI/CD中自动更新依赖版本。

#### 7.3.2 依赖审查

新增依赖需经过技术负责人审批。禁止使用存在已知安全漏洞的依赖库。定期更新依赖版本，修复安全漏洞。
